# 画布渲染器

状态：现行架构为第 10 节的统一渲染器；窗口不是 OpenGL（macOS、软件渲染）时画布走软件路径。
范围：编辑画布（选择 / 变形 / 编辑 / 绘画 / 模拟）的贴图与辅助层、纹理工作区的纹理集页面、预览画布的两种后端，以及播放与跟踪会话（第 11 节）。

渲染器不使用 `org.umamo.render` 下的渲染代码，只读取模型数据：`PuppetModel` / `Drawable` / `DrawableMesh` 和 `RigCanvasSupport.evaluate` 给出的形变结果。形变在 CPU 上计算，GPU 只负责贴图三角形、遮罩、着色与辅助线。没有可用 GPU 时由 `SkiaRigPainter` 软件绘制，它在第一次绘制时才转换图集页，GPU 绘制的画布不为它付出转换和内存；设置中的软件渲染开关同时作用于编辑画布与纹理集页面。

## 1–9. 早期方案（已取代）

原编辑画布在 CPU 上逐像素填充：贴图由 Skia 按三角形从 4096 贴图页采样，辅助层由 Java2D 画进整张 `BufferedImage`。示例 `tml`（24 个网格、3467 个顶点、一张 4096² 页，画布 1600×1000）上，CPU 形变只需 0.3–0.7 ms，而贴图绘制适配缩放约 26 ms、4× 缩放约 82 ms，Java2D 网格线框 12–20 ms，缩放、拖动和改参数时一帧可超过 100 ms。

第一版 GPU 渲染器因此用一个独立的 OpenGL 3.3 离屏上下文（隐藏 GLFW 窗口与专用线程），以 PBO 异步回读成 Skia 图交给 Compose，并在帧到达前按镜头重投影上一帧。这一路线先后把贴图、遮罩与着色（共用软件与 GPU 的绘制列表 `ArtworkDrawList`）、全部辅助层（`RigGuides`，与 Java2D 的覆盖率测试）、绘画笔触的局部纹理上传和纹理集页面搬上 GPU。它的代价是第二个上下文、跨线程同步、显示晚 1–2 帧以及每帧的回读拷贝；第 10 节的统一渲染器去掉了这些，独立上下文与回读只留在测试源码（`GlHost`）中，供无窗口时与软件绘制对照。

启动日志会写出窗口与编辑画布各自的渲染方式（例如 `窗口渲染：SOFTWARE_FAST`、`编辑画布渲染：GPU（…）`）。若窗口为 SOFTWARE，整个界面由 CPU 合成，各面板与动画都会变慢，这与画布渲染器无关，需要从显卡驱动或 Skiko 的渲染后端设置入手。

## 10. 统一渲染器（现行）

编辑画布、纹理集页面和两种预览后端共用一个渲染器，全部在**窗口自己的 Skia OpenGL 上下文**里、在绘制窗口的线程上运行，画进 Skia 持有的纹理，Compose 在同一帧画出。没有第二个上下文、没有上下文间共享与同步、没有任何像素离开 GPU。

### 10.1 上下文与轮次

- Windows 上 `SkiaGpu.requestOpenGl()` 在创建窗口前让 Skiko 使用 OpenGL（默认是 Direct3D）；用户显式设置的 `skiko.renderApi` / `SKIKO_RENDER_API` 保持不变。Linux 上 Skiko 本来就用 OpenGL。窗口不是 OpenGL（macOS、软件渲染）时画布走软件路径，预览报告原因。
- `SkiaGpu.of(window)` 从窗口的 `SkiaLayer` 读出 Skiko OpenGL 重绘器的上下文句柄与绘制它的 `DirectContext`（反射，Skiko 未公开），得到 `WindowGpu`。每个窗口（主窗口、浮动停靠窗口）各有一个，资源互不共享。
- **轮次**（`WindowGpu.turn`）：只在该上下文正当前时执行（`wglGetCurrentContext` / `glXGetCurrentContext` 比对），开始和结束都把 Skia 留下而绘制方不会自己复位的状态恢复为 GL 默认值（模板裁剪测试、采样器对象、像素缓冲、行长度、默认顶点数组上的缓冲与属性等），结束时 `DirectContext.resetGLAll()` 让 Skia 重新设置自己的状态。
- 轮次出现在两处：画布绘制时（`CanvasGpu.draw`、预览画布的 `drain`），以及包在窗口渲染委托外层、每帧 Compose 绘制之前执行的投递任务（`WindowGpu.post`，用于加载、释放和不由画布触发的工作）。
- `GpuTarget`：每个视图一张只增不减的纹理（Skia 以 `Image.adoptTextureFrom`、`TOP_LEFT` 接管）加深度模板缓冲。内容在左上角、首行在上；按 GL 习惯自下而上绘制的（Cubism）先画进场景缓冲，再用 `glBlitFramebuffer` 垂直翻转拷入。每帧覆盖同一张纹理：上一帧对它的采样在同一上下文中更早提交，GPU 按序执行，无需围栏。

### 10.2 编辑画布与纹理集页面

`CanvasGpu.draw(window, viewId, key, scene)` 在画布的绘制里同步执行：键未变就直接返回上一帧，不碰 GL；键变了才构建场景、在轮次中由 `GlCanvasRenderer.draw` 画进视图纹理，当帧画出。没有排队、回读和重投影，平移缩放即时就是精确帧。`GlCanvasRenderer.render`（离屏帧缓冲 + 读回）只留给测试在无窗口的上下文（测试源码中的 `GlHost`）上与软件绘制对照。

- 编辑画布：镜头是一个 uniform，平移缩放不上传数据；贴图页预乘、生成 mipmap；遮罩写模板缓冲，选中 / 悬停着色与变暗不改几何，软件与 GPU 路径共用同一份绘制列表（`ArtworkDrawList`）。辅助层（网格线框、变形器网格与角标、旋转指针、选中框、变形路径）由 `RigGuides` 给出与软件绘制相同的几何，名称与点序号是 Compose 文字。绘画时草稿贴图（`PaintScene`，草稿栅格大小）按合并后的脏矩形以 `glTexSubImage2D` 局部上传，画在叠加层之后。
- 纹理集页面（`AtlasScene`）：图块为 `TextureQuad`（各图层栅格按数组实例上传一次，放大到 2 倍以上按纹素采样；按网格排布的图块先把单元格写入模板），热力图为 `FillBatch`，网格线框为 `LineBatch`，被拖动或缩放的图块画在最上层；轮廓、选中、角点与框选是 Compose 绘制。纹理编辑经视图模型的串行队列（`queueTextureEdits`）依次提交，排队中的结果以 `TextureWorkspaceState.pending` 先显示。

### 10.3 预览后端

预览画布有两个后端，在预览左侧工具栏最上面的「运行时」一项（Cubism SDK / p2lrt · 标准 / p2lrt · 扩展）或左下状态胶囊的菜单里选择（应用设置，不随工程保存）：

| 后端 | 模型 | 求值与绘制 |
| --- | --- | --- |
| Cubism SDK | 导出的 moc3（`CubismRuntimeBundle`） | 官方 Cubism 5-r.5 运行时（`CubismSdkPreviewSession`） |
| PSD2Live 运行时（p2lrt） | 导出的 `.p2lrt`（`RigIrCompiler.compile(simulations = true)`） | `runtime/` 求值，`P2lrtGlRenderer` 绘制（`P2lrtPreviewSession`） |

- 两者都只渲染工作区时钟给出的完整姿势，不运行自己的动作或拖动；p2lrt 的扩展（高级）模式在每个视图的模型上开启 `p2l_set_advanced` 的功能。实时模拟与碰撞由**物理开关**控制，与播放无关：物理开启时以 `p2l_update` 按帧时间推进（暂停时也继续摆动，帧泵不进入静止等待），运行时自己的物理同时运行；物理关闭时关掉模拟与碰撞，显示烘焙的摆动，只保留蒙皮与精确链接，以 `p2l_evaluate` 求值。
- `PreviewSessions` 把两者放在同一个接口后：Cubism 库起不来时自动改用 p2lrt 并写日志；两者都不可用时，画布才用编辑画布的绘制路径兜底。
- 原生调用都是 `GpuExecutor` 的任务：应用里在窗口轮次中执行（`PrimaryGpuExecutor`、`WindowGpu.post`），测试里在普通线程上执行。帧泵每帧请求一帧后递增画布读取的计数，画布绘制时先 `drain` 执行本帧的渲染任务，再画该视图的纹理，所以显示的是刚请求的那一帧。
- Cubism 在主窗口上下文中以 `Live2D_Init` 初始化，以 `Live2D_Draw` 画进当前帧缓冲。框架的着色器等状态只存在于一个上下文，所以浮动窗口里的预览画布由 p2lrt 绘制。Cubism 的渲染器从客户端内存取顶点，需要兼容配置的上下文（Skia 在 Windows 上是传统兼容上下文）；核心配置下报告错误而不绘制。
- 原生桥接：旧版 `Live2D_CreateModelFromMemory` 总是切换到桥接自己的隐藏上下文，模型会落到错误的上下文里。重新构建的桥接导出 `Live2D_UsesCallerContext`，`Live2D_Init` 之后内存加载也使用调用方上下文；旧桥接在此模式下改为从临时文件加载（`Live2D_CreateModel`），每次重载都完整重建。
- p2lrt 的编译在独立线程上进行；网格与贴图页按上下文上传（`GpuResources.service`），每个视图一个运行时实例。

### 10.4 帧率

预览的帧泵在每个显示刷新（`withFrameNanos`）请求一帧；帧率上限是应用设置（跟随显示器 / 30 / 60 / 120，默认跟随显示器），与工程的物理帧率无关，物理在其固定步长之间插值。多个预览同时可见时不再限制为每个 30 FPS。

高刷新率下一帧的时间几乎全在 CPU 上（`PreviewFpsTool`，240 Hz，编辑工作区）：Skia 把整个窗口的录制翻译成 GPU 工作约 2 ms、提交约 1.8 ms，GPU 执行只要约 0.5 ms；预览运行时与 Cubism 的求值不到界面线程的 2%。翻译中很大一部分是为抗锯齿的路径、圆角与椭圆在 CPU 上计算覆盖率，改由 GPU 多重采样即可省掉。Skiko 的窗口表面是单采样的，所以 `MultisampledWindow` 把 Compose 每帧录制的画面回放到窗口大小的 4× MSAA 纹理，窗口只画这一张纹理（`psd2live.msaa` 设采样数，0 关闭）。必须先录制再回放：直接把 Compose 画进该纹理时，其图层（Skiko 渲染节点）的提交反而慢数倍。8× 比 4× 慢。实测编辑工作区（不等垂直同步）每帧从约 7.5 ms 降到约 6.1 ms。

高刷新率下的预算（`PreviewFpsTool`，RTX 4080 笔记本、240 Hz）：Windows 上 Skiko 每帧在界面线程上依次做 Compose（重组、布局、录制绘制）、Skia 把窗口的录制回放到 GPU、交换缓冲与 `glFinish`，再以 `DwmFlush` 等下一次刷新。一帧超过 4.17 ms 就要等两次刷新，落到 120 FPS。Compose Desktop 对任何变化都重画整个窗口，面板没变也要回放其全部绘制：编辑工作区仅此一项每帧约 5–6 ms。因此预览帧不经过 Compose，由窗口合成：

- **窗口合成器**（`WindowCompositor`，装在 `WindowGpu` 的渲染委托里）：每帧先唤醒预览帧泵并执行 GPU 任务（渲染预览纹理），再让 Compose 照常运行并录制到一张廉价的 Picture；只有场景的 `SnapshotInvalidationTracker` 报告过重绘或重排请求（其回调被包了一层计数）或窗口尺寸变化时，才把录制回放进缓存纹理；缓存纹理与上面的窗口目标一样是多重采样的（`psd2live.msaa`），不合成时窗口仍走 `MultisampledWindow`。窗口画面是各 `CompositedView`（预览背景、画布边框与最新帧）之上叠缓存纹理。Compose 内部经反射取得；拿不到、或窗口上下文不是当前上下文时按原方式绘制（`WindowGpu.composited` 为假）。`-Dpsd2live.compositor=false` 关闭。
- **预览画布挖洞**：合成时，使用原生帧的预览画布登记 `CompositedView` 并以 `BlendMode.Clear` 清掉自己的区域，其后绘制的工具栏、菜单仍在缓存画面里、位于预览之上。画布的绘制与组合都不读逐帧状态：帧泵在挖洞时不递增 `previewTick`，组合只读后端、扩展模式这类少变的值。
- **帧泵**等 `WindowGpu.awaitFrame` 而不是 Compose 的帧时钟（帧时钟上有等待者，Compose 每帧都要重画），在 `Dispatchers.Main.immediate` 上运行，于该帧开头内联请求预览帧。
- 播放中写入文档状态的预览姿势降到每 0.5 秒一次：每次写入都会让读取状态的面板重新组合、窗口整幅重画。面板读 `livePoseShown`（最多约 60 Hz）；参数行只在轨道与二维面板的绘制、数值文本和重置按钮状态处读取实时值，数值框获得焦点前是文本；不显示姿势的面板（层级树、骨骼、历史、日志、模型预设、图层表）在只有姿势变化时保留原状态实例（`withoutPlayingPose`）。
- `GridIcon` 绘制一次到位图，之后每帧一次贴图，替代数条抗锯齿路径。

实测：编辑工作区不等刷新时约 1.8 ms 一帧（此前 9.5 ms），等刷新时约 215 FPS；预览工作区约 230 FPS。动画与物理工作区的参数面板、摆锤画布在播放时持续变化，每次都要整幅重画，约 100–170 FPS；要进一步提高，需要按面板缓存。合成与原方式在暂停时的画面逐像素一致（`PSD2LIVE_CAPTURE=1` 对比）。

### 10.5 p2lrt 的绘制规则

与网页播放器一致：按 `p2l_render_order` 由后到前；贴图预乘上传并生成 mipmap，片元先还原直通色再乘乘算色、叠屏幕色，按网格透明度输出预乘色；遮罩写模板（纹素透明度 ≥ 0.5 才算覆盖，反向遮罩取不等）；混合按 Cubism 的预乘组合（普通、加算、乘算，扩展模式退回最接近的基本模式）；网格要求时剔除背面。相机沿用 Cubism 的取景参数（画布高度占短边 × `scale`，偏移为裁剪空间单位），两种后端取景一致。

### 10.6 编辑画布软件路径的遮罩

`SkiaRigPainter` 的遮罩不再把遮罩网格的全部三角形拼成路径再裁剪：被遮罩的部件画进一个以其三角形包围盒为界的图层，遮罩网格的并集以 `DST_IN` 图层合成上去，效果与 GPU 路径的模板缓冲相同（按几何覆盖）。

### 10.7 验证

`PreviewWindowTool` 打开真实窗口：编辑画布与两种预览后端都在窗口的 Skia 上下文中出帧，帧从 GPU 读出核对（只读视图纹理，不截屏）；在 RTX 4080 笔记本上两种后端播放时都超过 100 FPS，无帧率锁。工具带看门狗，窗口卡住两分钟即转储线程并退出。

## 11. 播放与跟踪会话

画布的播放、鼠标跟踪按钮与动画面板共用应用层的播放会话（`WorkspacePlaybackSessions`），属于进程临时会话，不进入工程或历史。

- 打开动作时，画布与动画面板共同播放 / 暂停该动作；没有动作打开时控制待机。动作自然结束、交叉暂停与恢复都由会话记录，不只改本地开关。
- 鼠标事件只更新指针坐标，下一个时钟帧再求值；作者姿态提交后保留跟踪状态和暂停的播放头。时钟帧在物理合成之后发布，迟到帧不能覆盖控制命令之后的播放头或姿态；工程重开会拒绝旧会话的帧。
- 两种预览后端都消费会话给出的完整姿态，不运行自己的动作、拖动或物理时钟（见 §10.3）；软件预览使用同一结果。
- 鼠标跟踪是独立于待机与动作的合成步骤。默认即时映射；预览工具栏的「平滑跟踪与身体 Y」开启后改用串联指数响应（`PreviewAnimationClock`）：头部响应率 18/s、身体 10/s，约 150 ms / 350 ms 达到固定目标的九成，身体保留较短的滞后；按经过的时间解析更新，不同帧率下响应一致，零时间步保持原姿态。该开关随工作区呈现保存，旧工程缺省关闭；切换算法保留指针位置，关闭跟踪立即停止跟随。
- 编辑后的预设动作沿用面板的 preset ID；控制命令清除旧的渲染帧，调整播放头后不残留上一次的姿态。
