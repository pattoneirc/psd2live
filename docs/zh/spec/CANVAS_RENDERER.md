# 画布渲染器重写：架构设计

状态：P0–P2 已实现，P4 大部分完成（见第 9 节）
范围：编辑画布（选择 / 变形 / 编辑 / 绘画 / 模拟）的贴图与辅助层绘制；预览画布的 Cubism 原生路径不在本次范围内。

## 1. 结论

编辑画布的卡顿来自**在 CPU 上逐像素填充**：贴图由 Skia 按三角形从 4096 贴图页采样，辅助层由 Java2D 画进整张 `BufferedImage`，两者都随画布尺寸和缩放倍数线性变贵。形变计算只有 0.3–0.7 ms，不是瓶颈。

新架构是一个**本项目自己的** GPU 渲染器：

- 独立渲染线程持有一个 OpenGL 3.3 core 离屏上下文，通过第三方库 LWJGL（含 GLFW）创建。
- 形变仍在 CPU 上算，算出的世界坐标每次变化时上传给 GPU。GPU 只负责它擅长的事：贴图三角形、遮罩、着色、辅助线。
- 平移和缩放只改一个矩阵 uniform，不重新上传任何数据。
- 结果经 PBO 异步回读成一张 Skia 图交给 Compose 显示，与目前流畅的 Cubism 预览路径相同。
- Compose 侧先按新镜头变换上一帧，所以平移、缩放即时跟手。
- 现有 `SkiaRigPainter` 保留为没有 GL 时的兜底。

不使用 `org.umamo.render` 下的任何渲染代码（`PuppetRenderer`、`RenderDevice`、`GlRenderDevice`、其着色器、回读与渲染目标类）。渲染器只读取模型数据：`PuppetModel` / `Drawable` / `DrawableMesh` 和 `RigCanvasSupport.evaluate` 给出的形变结果。这是全应用共用的数据模型，不属于渲染代码。

## 2. 现状与测量

测量条件：示例 `tml`（24 个网格、29 个变形器、3467 个顶点、一张 4096² 贴图页），画布 1600×1000，CPU 栅格。

| 每帧工作 | 适配缩放 | 4× 缩放 |
| --- | --- | --- |
| CPU 形变整模（`RigCanvasSupport.evaluate`） | 0.3–0.7 ms | 同左 |
| 录制贴图绘制指令 | ~1 ms | ~1 ms |
| **绘制贴图（`SkiaRigPainter`，CPU）** | **26 ms** | **82 ms** |
| **Java2D 画全部网格线框** | **12 ms** | **16–20 ms** |
| `BufferedImage` → Compose 图像（画布大小） | 4 ms（原 10 ms） | 同左 |

各模式的表现：

- **静止或悬停**：上一轮已把贴图栅格化缓存，每帧约 1 ms，所以界面动画不再卡。
- **缩放、编辑拖动、改参数**：缓存失效，每次变化都要重做上表中的加粗项。4× 缩放时一帧超过 100 ms。缓存方案在稳定下来那一帧还会再做一次 CPU 栅格化，所以缩放每停一下就多一次约 80 ms 的卡顿。
- **预览画布不卡**：贴图由 Cubism 原生库在 GPU 上画，Java 侧只回读并显示一张图。"GPU 渲染、回读、显示"这条路径在本应用里已被证明可行。

结论：在 Compose 的 Skia 画布上做 CPU 像素填充无法优化到可用，必须换渲染路径。

## 3. 目标

| 指标 | 目标 |
| --- | --- |
| 平移 / 缩放 | 每一步 UI 线程 ≤ 2 ms，画面即时跟手；精确帧在 1–2 帧内到达 |
| 编辑拖动（单网格形变、移点、笔刷） | UI 线程每帧 ≤ 4 ms（含 CPU 形变）；GPU 每帧 ≤ 4 ms（4K 画布、整模） |
| 静止 | 不产生任何渲染工作 |
| 画质 | 与现有编辑画布一致：线性过滤、遮罩裁剪、选中 / 悬停着色、未选中变暗；支持 HiDPI，可选 MSAA |
| 兜底 | 拿不到 GL 3.3 时自动回退现有 Skia 路径，功能不缺 |

## 4. 总体架构

```
UI 线程（Compose）                                  渲染线程（GL 3.3 core，离屏上下文）
┌────────────────────────────────┐  CanvasScene   ┌─────────────────────────────────────┐
│ CanvasViewport                 │ ────────────▶ │ CanvasGpuRenderer                   │
│  · 镜头、交互、编辑器           │ (不可变快照,  │  ├ TextureCache   贴图页 → GL 纹理   │
│  · 形变：按 (模型, 姿势) 缓存   │  最新者胜)    │  ├ MeshCache      UV / 索引（静态）  │
│  · CanvasFramePresenter         │               │  │                位置（动态）      │
│     画最近一帧 + 镜头重投影     │               │  ├ ArtworkPass    贴图、遮罩、着色   │
│  · 轻量交互层（Skia 矢量）：    │               │  ├ OverlayPass    线段 / 点实例化    │
│     手柄、光标、笔刷、文字      │ ◀──────────── │  └ Readback       PBO 三缓冲         │
└────────────────────────────────┘ RenderedFrame └─────────────────────────────────────┘
                                   (Skia 图 + 镜头)
```

新代码放在新包 `io.github.psd2live.render`，渲染线程上的全部 GL 调用都在这个包里。

### 4.1 上下文与线程：`GlHost`

- 新增依赖 `org.lwjgl:lwjgl-glfw`（及各平台 natives，与现有 `lwjgl`、`lwjgl-opengl` 同一 BOM）。
- 用一个**隐藏的 GLFW 窗口**创建 3.3 core 上下文，只用它的 FBO，不显示。
- 一个专用线程（`psd2live-canvas-gl`）独占这个上下文，全部 GL 调用都在这里；对外只暴露投递任务的接口，与 `CubismSdkPreviewSession` 的原生线程模式一致。
- 启动时检测 GL 版本与扩展；失败就记录原因并报告不可用，画布回退软件路径。
- 平台：
  - Windows 原生可用。
  - Linux 需要 X11/GLX，与 Cubism 原生预览的要求相同，XWayland 可用。
  - macOS 上 GLFW 必须在主线程创建窗口：首版在 macOS 直接走兜底路径。
- 与 Cubism 原生预览互不干扰：两个上下文、两个线程，不共享资源。

### 4.2 数据流：几何在 CPU，像素在 GPU

**形变**：留在 UI 线程。按 `(模型身份, 姿势)` 只算一次，拾取、辅助层、渲染三方共用同一份 `DeformedGeometry`。现在编辑器和画布各算一次，统一成一个 `CanvasGeometry` 缓存。示例模型整模 0.3–0.7 ms，在预算内。模型变大后若超出，再改为只重算受编辑影响的网格（见第 7 节 P3）。

**`CanvasScene`**：UI 线程每次变化时生成的不可变快照，只放引用和小值：

- 模型身份与 `DeformedGeometry`（世界坐标，已形变）；
- 贴图页身份（`PackedAtlas`）；
- 镜头：缩放、平移、画布像素尺寸、像素密度；
- 绘制列表：每个网格的可见性、绘制顺序（已应用覆盖）、不透明度、遮罩来源、着色色与强度（选中 / 悬停 / 变暗）；
- 辅助层批次（见 4.5）；
- 背景设置。

**上传规则**（渲染线程）：

| 变化 | GPU 工作 |
| --- | --- |
| 镜头（平移 / 缩放） | 只改投影矩阵 uniform |
| 姿势、编辑拖动 | 重传**几何对象变了的**网格的位置 VBO；示例全模型也只有约 28 KB |
| 网格拓扑（细分、切割、重建） | 重传该网格的 UV 与索引 |
| 贴图页更新（重新打包、绘画提交） | 重传该页纹理 |
| 选中、悬停、可见性、顺序 | 不上传，只改绘制列表 |

判断"变没变"用数组身份：编辑路径是写时复制，没碰的网格保持同一个数组实例，比较引用即可，不必逐元素比较。

### 4.3 贴图：`ArtworkPass`

- **网格存储**：每个网格一个 VAO，三个缓冲：
  - UV：`STATIC_DRAW`；
  - 索引：`STATIC_DRAW`，32 位，不受 65535 限制；
  - 世界坐标：`DYNAMIC_DRAW`，用 `glBufferSubData` 更新。
- **着色器**：一个顶点着色器，用世界坐标乘投影矩阵；一个片元着色器，采样贴图页，再乘不透明度、混合着色色。
- **贴图**：贴图页上传一次，线性过滤；按需生成 mipmap，缩小时不闪。
- **遮罩**：用模板缓冲。先把遮罩来源网格写入模板（不写颜色），再以模板测试绘制被遮罩的网格；反向遮罩反转测试条件。与现有 `SkiaRigPainter` 的裁剪语义一致，但不再每帧构造路径。
- **着色**：选中、悬停、变暗都是 uniform，不改几何：
  - 悬停色在着色器里与贴图按现有 `SELECTION_TINT_STRENGTH` 强度混合，只作用于该网格自己的像素，所以遮罩和遮挡都自然正确；
  - 变暗是不透明度乘数。
- **绘制顺序**：由 UI 侧排好序放进 `CanvasScene`，渲染线程按序绘制，不在 GL 侧排序。
- **模拟预览的直接位置**：模拟给出的顶点位置在 UI 侧并入 `DeformedGeometry`，对渲染器而言就是普通的位置更新。
- **姿势快照幽灵**：同一模型的第二份几何以 0.6 不透明度画进一个离屏纹理，再合成到主目标，避免重叠部件互相叠暗。

### 4.4 输出与显示：`Readback` + `CanvasFramePresenter`

- **渲染目标**：每个画布一个 FBO（颜色 + 深度 / 模板），按历史最大尺寸只增不减分配。HiDPI 下按设备像素渲染；MSAA 可选，默认 4×，解析到单采样纹理后回读。
- **回读**：三个 PBO 轮转，第 N 帧发起 `glReadPixels` 到 PBO，第 N+1 帧映射取回第 N 帧，不阻塞 GPU。行顺序在着色器投影里直接翻转，省掉 CPU 翻行。
- **转换**：取回的 RGBA 字节整块装进 Skia `Bitmap`（RGBA_8888，预乘），用 `asComposeImageBitmap()` 包装，不经过 `BufferedImage`，不做逐像素转换。
- **显示**：每帧附带渲染时的镜头。Compose 显示时，若当前镜头和该帧镜头不同，就按差值对图像做平移和缩放后再画。这样平移、缩放在 UI 线程上即时跟手，GPU 帧到达后无缝替换。
- **代价**：显示比输入晚 1–2 帧（约 16–33 ms），与现在的预览画布相同。拖点时手柄由 Compose 即时绘制，跟手不受影响。

### 4.5 辅助层：`OverlayPass`

替代 Java2D 辅助层（`CanvasViewportComposable` 中的 3b–3e 段）和 `CanvasEditorOverlay` 里成批的几何。

- **数据**：UI 侧把辅助层整理成按样式分组的批次，一组一个样式（颜色、线宽、虚线），内容是世界坐标的线段或点：
  - 网格线框：直接引用网格索引与 4.2 中已上传的位置 VBO，**不再在 CPU 上逐边投影**；边列表按索引数组身份缓存；
  - 变形器网格、旋转参考、变形路径、包围框：点数少，CPU 生成后作为小批次上传。
- **绘制**：
  - 线段每条展开成一个四边形，实例化绘制，屏幕空间线宽，片元里按距离做抗锯齿；
  - 点是实例化圆点，带描边；
  - 每帧绘制调用次数等于样式组数，个位数到十几次。
- **留在 Compose 的部分**：手柄、光标、笔刷圈、文字标签、右键菜单等少量、需要字体或必须即时跟手的元素，用 Skia 矢量直接画，不经 `BufferedImage`。数量与画面大小无关，几十个以内。

### 4.6 拾取

拾取继续在 UI 线程用 4.2 的共享几何（CPU，已缓存），与渲染用的是同一份坐标，不会出现"画的和点到的不一致"。包围框、角标等派生数据按几何身份缓存（上一轮已为悬停做了这部分）。

### 4.7 编辑拖动的一帧

1. 指针移动：`CanvasEditor` 生成写时复制的 `preview` 模型（现有逻辑）。
2. UI 线程：
   - `CanvasGeometry` 重算形变，示例整模 < 1 ms；
   - 生成 `CanvasScene` 并投递，只含引用。
3. 渲染线程：
   - 重传位置变了的网格的 VBO，通常一个；
   - 画贴图和辅助层；
   - 发起回读。
4. 下一帧：Compose 显示新图并画手柄。

UI 线程不做任何像素填充。

### 4.8 兜底与接口

`CanvasViewport` 只依赖一个接口，GPU 与软件两个实现：

```kotlin
interface CanvasRenderer : AutoCloseable {
    val available: Boolean
    fun submit(viewId: String, scene: CanvasScene)
    fun frames(viewId: String): StateFlow<RenderedFrame?>
}
```

- `GpuCanvasRenderer`：本设计。
- `SoftwareCanvasRenderer`：把现有 `SkiaRigPainter`、`CachedSkiaPicture` 和 Java2D 辅助层收拢到接口后面，行为与今天相同。

GL 不可用时（拿不到上下文、macOS 首版、驱动故障、渲染出错）自动用软件实现；设置里提供"强制软件渲染"开关用于排查。

## 6. 风险与验证

| 风险 | 对策 |
| --- | --- |
| 新渲染器与现有画面不一致（遮罩、着色、顺序） | P0 做**对照测试**：Xvfb + Mesa llvmpipe（支持 GL 4.5 core）下，用 GPU 渲染示例 `tml`、`ds` 的多组姿势、选中与悬停状态，与 `SkiaRigPainter` 的 CPU 结果逐像素比对，误差设阈值；测试进 CI |
| 显示晚 1–2 帧 | 镜头重投影保证平移和缩放跟手；手柄、光标由 Compose 即时绘制 |
| 大模型的 CPU 形变超出预算 | 先测；超出时只重算编辑涉及的网格及其变形器链（P3） |
| 驱动 / 平台差异 | 启动能力检测、自动兜底、"强制软件渲染"开关；渲染错误时降级并写日志，不让画布空白 |
| 显存（4K、4× MSAA 约 130 MB / 画布） | MSAA 可在设置中关闭；只增不减的分配，后续可加空闲回收 |
| 多画布同时编辑 | 共享贴图与网格缓存，每画布一个目标；同一 GL 线程串行，按画布限速 |

## 7. 分阶段计划

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **P0 地基** | `GlHost`、`Readback`、`Shaders`、`ArtworkPass` 最小版（贴图 + 不透明度）；对照测试；画布性能测试工具（Xvfb 下驱动真实窗口，测缩放 / 拖动 / 平移的帧时间） | 示例两份 PSD、多组姿势对照通过；CI 的 Xvfb 下可跑 |
| **P1 贴图上 GPU** | 遮罩、着色、变暗、幽灵层；`CanvasGeometry`、`GpuCanvasRenderer`、`CanvasFramePresenter`、镜头重投影；设置开关，默认开启 | 4× 缩放连续滚轮、单网格拖动：UI 线程每帧 ≤ 4 ms；与旧路径截图一致 |
| **P2 辅助层上 GPU** | `OverlayPass`；迁移网格线框、变形器网格、旋转参考、变形路径、包围框；删除 Java2D 辅助层 | 显示全部网格线框时，4K 画布帧时间仍达标 |
| **P3 编辑增量化** | 画布只订阅需要的窄状态，文档无关更新不再触发画布重组；必要时局部形变 | 参数面板、时间轴等的状态更新不再引起画布重绘 |
| **P4 收尾** | 绘画笔触改为 `glTexSubImage2D` 局部更新贴图；软件路径只作兜底；评估把软件预览路径也迁到 GPU | 旧缓存类只在兜底实现中保留 |

每个阶段单独提交、可回退；P1 起画布渲染方式由设置开关控制，出现问题可立即切回软件路径。

## 8. 不在本次范围

- Cubism 原生预览路径（已经流畅）。
- 导出与 Agent 视图渲染（`AgentViewRenderer`），可在 P4 之后接入同一渲染器。
- 混合模式（加算、乘算）：现有编辑画布也不显示，保持一致；若需要，加在 `ArtworkPass` 的混合状态里。
- 其他图形后端（Vulkan / Metal / Direct3D）。

| P2 辅助层上 GPU | 完成 | 网格线框、变形器网格与角标、旋转指针、选中框、变形路径（含宽度 / 硬度圈与转角菱形）全部由 GPU 绘制；名称与点序号为 Compose 文字。有 GPU 时 Java2D 辅助层整体跳过。路径用「模板只画一次」的折线绘制，半透明描边在转折处不会叠深。`RigGuides` 与 Java2D 的覆盖率测试：变形器 98% / 100%，路径 100% / 100% |
| P3 编辑增量化 | 部分 | 已去掉缩放时的整树重组；拖动时界面线程在 Java 代码中仅占约 5%，余下时间在窗口合成 |
| P4 收尾 | 大部分 | 帧读回直接写入显示用的 Skia 位图（每帧少两次整画布拷贝）；帧位图在界面线程上按代回收，内存有界；贴图开启 mipmap；姿势快照幽灵改由 GPU 帧以 60% 透明度绘制。绘画笔触改为每视图一张文档尺寸的绘画贴图：CPU 笔刷引擎不变，脏矩形合并后以 `glTexSubImage2D` 局部上传（预乘 RGBA），在叠加层之后以一个四边形绘制；被丢弃的场景会把上传并入下一帧，不丢笔迹。实测（Xvfb/llvmpipe，`paint-stroke` 阶段）GPU 45 fps、软件 30 fps。剩余：macOS 仍走软件路径 |
| P5 纹理集页面上 GPU | 完成 | 纹理工作区的纹理集页面与编辑画布共用 `CanvasRenderService`：`AtlasScene` 只含叠加层，图块是 `TextureQuad`（各图层栅格按数组实例上传一次、预乘、mipmap，放大到 2 倍以上按纹素采样；按网格排布的图块先把单元格写入模板再画），热力图为 `FillBatch`，网格线框为 `LineBatch`，被拖动或缩放的图块与其线框画在最上层。轮廓、选中、角点、框选仍是 Compose 绘制，悬停不重画任何纹素；帧未到时按镜头重投影上一帧。升维纹理集在实时页面图可用时从页面图裁取图块，否则走软件路径；软件渲染开关同时作用于此页。`AtlasFramePerfTool`（tml，无窗口，界面线程每帧中位数）：悬停软件 2.8 ms、GPU 1.4 ms，拖动图块 3.3 / 2.3 ms |

启动日志会写出窗口与编辑画布各自的渲染方式（例如 `窗口渲染：SOFTWARE_FAST`、`编辑画布渲染：GPU（…）`）。若窗口为 SOFTWARE，整个界面由 CPU 合成，各面板与动画都会变慢，这与画布渲染器无关，需要从显卡驱动或 Skiko 的渲染后端设置入手。
